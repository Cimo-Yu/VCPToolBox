# VCPdesktop 指针事件通道与三个事件黑洞（源码实证）

## 核心概念
在 VCPdesktop 中，"鼠标位置"并非由单一事件流提供。存在若干**接管指针的原生流程**，期间 `mousemove` 停止投递到渲染进程。任何"位置只由 mousemove 驱动"的实现（自绘光标、拖影、坐标 HUD、悬浮提示定位）都会在这些区间里卡在最后一个已知坐标上。

## 三个事件黑洞

### ① app-region drag（拖窗）
`css/base.css:100` `#desktop-title-bar { -webkit-app-region: drag; z-index:9999; height:32px }`。
拖窗由 OS 窗口管理器接管，期间渲染进程收不到 mousemove。
注意：现有 `#desktop-title-bar:hover { opacity:1 }` 能工作，**只证明 Chromium 在命中测试层跟踪 hover，不等于事件到达 JS**。此处不得跨层外推。
该属性运行期可改（`ui/globalSettings.js:318-341` 用 JS 在 `'drag'`/`''` 间切换）。

### ② HTML5 原生 dnd
拖拽期间浏览器进入 drag session，只发 `dragover`/`dragenter`/`dragleave`/`drop`，**不发 mousemove**。
`dragover` **携带有效坐标**——实证：`ui/dock.js:318` `getDragOverIndex(e.clientX, e.clientY)` 直接用它计算插入位置。故可将 dragover 接到同一位置更新回调。

VCPdesktop 内 dnd 通道全表：

### ③ 离窗 / 失焦 / 原生表面
指针移出客户区、窗口失焦、`<select>` 弹层或系统文件对话框打开期间无 mousemove。
**陷阱**：在此不能用 `window.blur` 作为判据——置底模式（`desktopHandlers.js:2643`，每 1.5s `pushToBottom` + 获焦即沉）会使 blur 成为高频常态事件。正确判据是 `mouseenter`/`mouseleave` 维护的 `pointerInside` 标志，blur 仅在 `!pointerInside` 时才视为离开。

## 处置原则
分两类：
- **能拿到坐标的** → 接到同一位置更新回调（dragover）。
- **拿不到坐标的** → 一律进入"失明"降级：隐藏自绘元素，交还系统默认表现。

判据：**"显示错误位置"比"暂时交还系统光标"严重得多**。后者是降级，前者是故障——用户会认为功能坏了，而降级只是短暂不美观。

## 挂件沙箱不会争夺 document 事件
`core/widgetManager.js` 的 `buildSandboxCode(widgetId, userCode)` 将挂件脚本包进 IIFE，其中 `document` 被替换为指向 shadowRoot 的伪对象：
```js
var document = {
    querySelector: sel => root.querySelector(sel) || _shadowRoot.querySelector(sel),
    getElementById: id => root.querySelector('#' + id),
    addEventListener: (type, fn, opts) => { root.addEventListener(type, _wrap(fn), opts); },
    body: root, head: _realDoc.head, documentElement: root,
    ...
};
```
故挂件内的 `document.addEventListener('mousemove', ...)` 实际挂在 `.widget-inner-content` 上，**无法在真实 document 上注册监听**。宿主侧的 document 级指针监听不会被挂件干扰。

`window` 则是真实 window 的 Proxy：`addEventListener` 透传但被包装计时并登记到 `_widgetData._windowListeners`（供 removeWidget 时清理），`setInterval/setTimeout/requestAnimationFrame` 被替换为登记版本，rAF 额外调用 `performanceManager.recordFrame(widgetId)`。故挂件**可以**在 window 上挂 mousemove——设计宿主侧监听时应放在 document 层以避开。

## 冻结协议与运动实现方式的关系
`core/visibilityFreezer.js` 冻结时给 body 加 `desktop-frozen`；`css/base.css:180` 规则为
`body.desktop-frozen * { animation-play-state: paused !important; transition: none !important; }`

推论：**用 `transform` 直写实现的运动不受冻结影响**，只有 CSS animation / transition / Web Animations / SMIL / rAF 会被停。这是双向事实：
- 好处：冻结期间仍需响应的元素（如指针跟随）无需特殊豁免。
- 坏处：期望被冻结的自定义运动若用 transform 直写，则不会自动停止，需自行实现 `vcp-freeze` 协议或依赖"无输入即无更新"。

freezer 明确**不监听 blur/focus**（源码注释：普通窗口覆盖也触发 blur，会导致过于灵敏），只用 `document.visibilitychange` + 可选 IPC `onWindowOccluded`。故渲染层自行使用 blur 不会与 freezer 冲突，但仍受置底抖动影响（见上）。

## 一般化判据
1. **把"运动"绑定到输入事件而非时间，冻结语义免费得到**——无输入即无更新，窗口被遮挡时循环自然停摆。与"零 rAF 壁纸架构"（运动交给 CSS animation / 合成器）是同一原理的两个应用面：JS 侧不持有时间循环。
2. **凡"压制某属性后又以该属性为输入"的设计必死**。例：全局 `cursor:none !important` 后再读 `getComputedStyle(el).cursor` 判断该画什么形状——抑制动作本身擦掉了判据。解法是另开只承载意图的通道（自定义属性），使外观与语义分轨。
