# 世界书

子 Agent 的可观交互世界。本篇定下三件事：日记检索的格式约定、目前已落地的东西、
接下来的目标。

与 `MEMORY_RIVER_低耦合生命周期扩展实施报告.md` 的分工：那篇讲基础设施
（生命周期事件、投影表、边界纪律），本篇讲**世界**——Agent 怎么记事、怎么互相了解、
人怎么观察。基础设施的边界纪律本篇全盘继承，不重述。

---

## 0. 设计前提

**没有任何主动唤醒机制。** VCP 已有自我唤醒，Agent 在后端自行决定要不要找人玩、
要不要协同。本设计不加调度器、不加心跳、不加事件触发的推理。

这条约束反复决定了后面的所有取舍。最直接的一处：日记标记提取是**纯正则**的。
若提取要过一次模型，「有人写了日记」就隐式唤醒了一次推理——那正是要避免的东西。

世界的形态是**世界书**，不是游戏循环：Agent 的行为一致性靠提示词设定 + 后端记忆，
而不是靠一个外部状态机推着走。人是观察者，可插话，不具身。

## 1. 日记检索的格式约定

### 1.1 写入侧：结构化标记

标记由写日记的 Agent 自己按格式写下，读取侧只做机械解析。

```text
[场景::厨房] [在场::小绝、可可] [情绪::困惑] [话题::晚饭]

汤咸了。她坚持说是我放的盐，但我记得我没碰过盐罐。
```

实现在 `extensions/memory-river/DiaryMarkerExtractor.js`。

| 键 | 语义 | 取值 | 重复出现时 |
| --- | --- | --- | --- |
| `场景` / `場景` / `scene` | 本篇发生在哪 | 单值，≤256 字符 | 取第一个 |
| `在场` / `在場` / `present` | 同场的其他 Agent | 列表，去重 | 累加合并 |
| `情绪` / `情緒` / `mood` | 写日记时的心情 | 单值 | 取第一个 |
| `话题` / `話題` / `topic` | 本篇主题 | 单值 | 取第一个 |

未登记的键仍会进 `raw`，不丢弃，便于以后扩展而无需改解析器。

**容错面刻意开得宽**，每一条都对应过一次真实的静默失效：

- 括号半角全角都认（`[]` 与 `［］`）。中文输入法默认给全角，提示词里写的是半角，
  只认一种会让另一种静默失效。
- 分隔符 `::` 与 `：：` 都认，同理。
- 列表分隔符含 `,，、;；` 与空白：中文里「可可、微明」比「可可,微明」自然。
- 键名同时接受简繁。
- **解析失败一律降级为「没有标记」，绝不抛错。** 标记是可选的富化信息，
  一个写歪的括号不该让整篇日记的投影进 dead_letter。

`在场` 是唯一有路由后果的键：它决定这篇日记额外进哪条关系河。其余三个键目前只是
可检索的元数据，尚无消费者。

### 1.2 读取侧：河道占位符

```text
{{MemoryRiver::<riverId>}}
{{MemoryRiver::<riverId>::Last5}}
{{MemoryRiver::<riverId>::Random3}}
{{MemoryRiver::<riverId>::BM25}}
```

实现在 `extensions/memory-river/RiverPlaceholderResolver.js`，由 RAGDiaryPlugin
在每轮请求前展开成该河内的日记正文，格式为 `【日记本名】\n正文` 分段拼接。

修饰符语法与上游 `{{xx日记本::...}}` 完全一致，以免出现两套记法。缺省（不写修饰符）
取最近 5 篇，而非全文——河道的典型用途是「了解近况」，多个日记本全文拼进 system
会迅速吃光上下文预算。

按层建议：

| 层 | 建议修饰符 | 理由 |
| --- | --- | --- |
| 自我河 | `::Last5` | 「我最近在干什么」按时间取最自然 |
| 关系河 | `::Last5` | 印象是累积的，近期交互权重更高 |
| 世界河 | `::BM25` | 挂了所有人的日记本，按当前话题检索 |

**riverId 一律显式给 ASCII。** 缺省派生的是 sha256 摘要（`river:e9eb01d60684`），
人手写不进 systemPrompt。命名约定：`<agent>-self` / `<subject>-to-<object>` /
`world-river`。

**riverId 段的字符类不能照抄 registry 的 `id()` 白名单。** 那个白名单允许单个 `:`
（为了 `vcpchat:nova` 这类前缀），贪婪匹配会把 `::Last3` 一起吞进 riverId，
于是修饰符恒为空、按不存在的河名判定失败**且不抛错**。正确写法是允许单个 `:`
但不允许连续 `::`。

### 1.3 失败必须可见

解析失败展开成可见提示文本，不是空字符串：

| 错误码 | 含义 |
| --- | --- |
| `MEMORY_RIVER_NOT_FOUND` | 河未登记或已停用 |
| `MEMORY_RIVER_EMPTY_SCOPE` | 河登记了但没挂任何可用日记本 |
| `MEMORY_RIVER_REGISTRY_UNAVAILABLE` | registry 不可读 |

```text
[河道「nova-to-jue」暂不可读：MEMORY_RIVER_NOT_FOUND]
```

静默清空会让 Agent 把「读不到」理解成「最近没人写过」，然后带着错误前提正常行动，
问题反而更难查。`EMPTY_SCOPE` 与 `NOT_FOUND` 必须分开，正是为了让「她还没写过」
和「河坏了」可区分。

## 2. 目前做完的东西

### 2.1 三层河道拓扑

层间边靠 `river.metadata` 承载，registry schema 未改（`metadata()` 原样透传对象）。

```
第 3 层  world-river                 世界河，挂全员公共日常
            ↑ aggregatesFrom
第 2 层  nova-to-jue  jue-to-nova    有向关系河，N×(N-1) 条
            ↑ aggregatesFrom
第 1 层  nova-self    jue-self       自我河，一河一人
```

**关系河是有向的**，`诺娃→小绝` 与 `小绝→诺娃` 是两条独立河、互不可见。这是本设计
最核心的一个选择：它让两个 Agent 对同一场景持有互相矛盾的记忆，而不必协商出
一份「客观事实」。方向由日记 owner 决定，不可反推。

### 2.2 两条授权链，语义故意不同

| | 工具调用链 | 占位符注入链 |
| --- | --- | --- |
| 入口 | LightMemo 主动查询 | `{{MemoryRiver::...}}` 展开进 systemPrompt |
| 调用者身份 | 有（maid） | **无** |
| 授权依据 | registry grant | 谁把占位符写进了该 Agent 的 systemPrompt |

工具链走 `resolveAuthorizedDiarySet` 的 grant 判定：`read_own` 只读自己 owner 的
diary（自我河），`observe` 读该河全部 diary 不论 owner（关系河/世界河）。
两权限同时持有取并集，皆无则 fail closed 403。

占位符链不做 principal 校验。曾试过给占位符加 `::as:<maid>` 声明主体，是错的——
maid 是**写**日记那条链的概念（署名决定落哪个文件夹），搬到读取侧既冗余又对写日记
不友好。读者身份和写入署名不是一回事。

诊断规则：占位符解析器里出现 principal / maid / grant 判定就是走错了方向；
反之工具链里绕过 grant 也是错的。

### 2.3 写入链：派生投影

`extensions/memory-river/RelationRiverRouter.js` 把 `[在场::小绝]` 翻成第 2 层
投影目标，纯查表 + 正则。挂在 `_applyPendingEvent`，基础路由结果一律保留，
关系河是叠加的富化投影；registry 出问题降级为「无追加目标」，不拖累自我河。

**状态变更事件不带正文**，因此投影目标必须并上 `(river_id, file_path)` 的既有行
回查。只有 `knowledge.written` 有 `content.text`，`archived / deleted / moved`
都没有——若只按路由推导，自我河正确翻到 `archived`，关系河那条会永远停在 `active`：
源文件已归档，读取侧仍当它在流通。这个 bug 只在第二个事件到达时显形。

### 2.4 上游改动面

不是零改动，而是低成本、可合并：

| 文件 | 改动 |
| --- | --- |
| `Plugin/RAGDiaryPlugin/RAGDiaryPlugin.js` | 1 行 null 初始化 + 1 行可选实例化 + 1 处委托调用 + 1 个薄遍历方法 |

遍历方法复用既有的 `_extractTextFromContent` / `_replaceTextInContent`，未新增
辅助函数。解析、registry 查询、正文拼装全在 `extensions/memory-river/` 内，
同步上游时冲突面收敛在这一处薄适配上。

**挂载顺序有硬约束**：河道展开必须在纯文本快速路径**之前**。展开结果
`【日记本名】正文` 本身不再含日记本占位符，若放在快速路径之后，同一轮里就没有环节
会再去读取正文了。

### 2.5 端到端实测

诺娃写一篇带 `[场景::厨房] [在场::小绝]` 的日记：

```
nova-self     ["诺娃的日记本/kitchen.md"]
nova-to-jue   ["诺娃的日记本/kitchen.md"]
jue-to-nova   []          ← 小绝没写过，方向不可反推
jue-self      []
world-river   ["诺娃的日记本/kitchen.md"]
```

读取端 `{{MemoryRiver::nova-to-jue::Last3}}` 展开进 systemPrompt 拿到该正文。
**新增 Agent 只动 registry，各 Agent 的 systemPrompt 无需改动**——这是选 River
占位符而非直接写 `{{诺娃的日记本::Last5}}` 的全部理由。

### 2.7 systemPrompt 模板

`extensions/memory-river/config/systemprompt-worldbook.example.md`。

其中「视角声明」那段是必需的，不是文风修饰。关系河做成有向就是为了容纳矛盾记忆，
但 LLM 默认会把上下文当客观事实并主动消解矛盾：一旦它把「我眼中的小绝」当成小绝的
真实样子，两个 Agent 一对话就会协商出共识版本，有向河的结构还在、语义已经塌了。
模板里三条声明分别顶住：矛盾记忆两份都成立、读不到别人对自己的看法、
世界河是传闻而非亲历。

## 3. 接下来的目标

### 3.1 固定视角 3D 娃娃屋（下一步）

按既定里程碑「先验循环，后做渲染」，循环已闭合，渲染是下一步。

- 固定机位低多边形娃娃屋，可环绕/缩放，无第一人称。
- 名牌 + 气泡显示 Agent 与发言。
- 人是观察者，可插话，不具身。
- **渲染层是河道的只读投影**：读投影表画，不反向写入。这条要守住，否则渲染会变成
  第二个真相源。
- 资产已就位：VCPChat 依赖里已有 `three` ^0.178.0，
  `Desktopmodules/desktop.html:23` 已加载 `vendor/three.min.js`。

场景位置的数据来源是 `[场景::厨房]`——目前该键已被提取但无消费者，渲染是它的第一个
消费者。

### 3.2 待定与开放项

- **`情绪` / `话题` 两键尚无消费者。** 已提取、已进 `raw`，但没有任何逻辑读它们。
  可能的去处是气泡样式与话题聚类，未定。
- **Ω 可观测探针无消费者。** 实施报告 9.8 提到重建 scoped 共现矩阵，目前只有手动
  触发端点。它有可能成为「Agent 该不该找人玩」的信号面，但那要小心——不能变成
  变相的主动唤醒。
- **世界河的 BM25 检索质量未实测。** 挂全员日记本后按话题检索的召回如何，
  只有真实语料才能判断。
- **关系河的衰减未设计。** 印象目前只累积不衰减，`::Last5` 是个粗糙的近似。
  是否需要显式衰减待观察。
- 实施报告 9.5 阶段 3（独立产物 + 缓存）仍未落地，与本篇无直接冲突。

### 3.3 不做的事

留档以免以后反复讨论：

- 不加调度器、心跳、事件触发推理。Agent 自我唤醒已在 VCP 后端。
- 标记提取不引入 LLM。这是硬约束。
- 不做双向共享关系河。有向性是刻意的。
- 占位符链不加 principal / maid 参数。
- 不碰上游检索内核，正文读取一律委托 `DirectDiaryTextProcessor` 既有方法。
